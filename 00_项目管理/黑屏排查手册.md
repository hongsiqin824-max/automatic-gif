# 预览排查手册（8901 工作台：黑屏 / 卡顿）

操作员反馈某场比赛工作台预览有问题时，先按本文档**分类**，再按对应章节定性、解决。
所有命令都在**服务器** SSH 终端执行。

## 先分清是哪一类

| 类别 | 操作员看到的现象 | 日志特征 | 去看 |
|---|---|---|---|
| **黑屏** | 画面一直是黑的，但进度在走 | 程序一直在跑、分片也在写；退出很少，或 `reason` 是编码类报错 | 第一章 |
| **卡顿** | 画面卡住、转圈，过十几秒又好，反复出现 | 短时间内多次 `preview_ffmpeg_exited` + `preview_ffmpeg_restarted`，每次 `uptime_seconds` 很短（十几到几百秒） | 第二章 |

## 先记住三条事实

1. **退出次数多 ≠ 有问题。** 比赛前后、推流方掉线时，源会拒绝播放，程序每 5 到 60 秒重试一次，一周累计上千次退出是正常的。要看的是**出问题那个时刻**的退出原因。
2. **线索在退出日志的 `reason` 里**，不在退出次数里。`3ec04a1`（2026-11-03）起，日志会跳过 `Last message repeated N times`，直接记被刷屏的那条原始警告，并附带 `stderr_tail`（退出前最后 5 条不重复的报错）。
3. **服务器 ffmpeg 是 5.1.10**（2026-11-01 核实）。它不支持 H.265（HEVC）的国际标准写法；国内私有写法的 H.265 任何版本都不支持。

## 通用步骤（两类都先做）

### 第 0 步：确认日志版本已上线

```bash
cd /opt/gif-monitor && git log --oneline -1
```

输出的提交必须是 `3ec04a1` 或更新。如果还停在更早的提交，先 `deploy-gif` 部署，否则日志里只能看到 `Last message repeated`，看不到真正的警告。

### 第 1 步：找比赛 ID

工作台地址里的数字就是比赛 ID。操作员只给了队名时，用队名里的一段搜（时间按实际改）：

```bash
journalctl -u gif-monitor --since "2026-11-04 08:00" --no-pager | grep '队名关键字' \
  | grep -oE '"match_id": "[0-9]+"' | sort | uniq -c
```

### 第 2 步：看这场的退出 / 重连时间线

把 `比赛ID` 换成实际数字：

```bash
journalctl -u gif-monitor --since "1 day ago" --no-pager \
  | grep '"match_id": "比赛ID"' \
  | grep -E 'preview_ffmpeg_exited|preview_ffmpeg_restarted|preview_history_resumed|preview_resource_switched' \
  | cut -c1-500
```

只看退出原因的统计：

```bash
journalctl -u gif-monitor --since "1 day ago" --no-pager \
  | grep preview_ffmpeg_exited | grep '"match_id": "比赛ID"' \
  | grep -oE '"reason": "[^"]*"' | sort | uniq -c | sort -rn
```

看全部比赛、排除「源没在推」的正常退出：

```bash
journalctl -u gif-monitor --since "1 day ago" --no-pager \
  | grep preview_ffmpeg_exited | grep -v "Operation not permitted" \
  | grep -oE '"reason": "[^"]*"' | sort | uniq -c | sort -rn | head
```

**怎么读**：
- 出问题的时刻**有** `exited` / `restarted` → 源在那时断了，按 `reason` 查下面对应章节的表。
- 出问题的时刻**没有**任何输出 → 我们的转码程序一直正常在跑。黑屏看第一章第 3 步；卡顿看第二章第 2 步（带宽）。
- `preview_history_resumed` 出现 → 重连成功、画面已接上，之前的回看缓冲还在。

## 第一章：黑屏

### 第 1 步：对照下表定性

| `reason` 里的原话 | 是什么问题 | 怎么解决 |
|---|---|---|
| `codec 12`、`codec id 12`、`Unsupported video codec` | 源用了国内私有写法的 H.265（老 ffmpeg 的 codec id 12） | **升级 ffmpeg 没用**。找推流方改推 H.264，或换一条源 |
| `hvc1`、`hev1`、`hevc`、`Video codec hevc not compatible with flv` | 源用了国际标准写法的 H.265 | 服务器升级 ffmpeg 到 7.x（见下方「升级 ffmpeg」） |
| 解码出错、`corrupt`、`Invalid data` | 推流本身损坏 | 找推流方 |
| `Last message repeated N times`（没有前面的原话） | 日志版本太旧，没记下被刷屏的警告 | 先部署 `3ec04a1`，等下一次再查 |
| 表里没有的新原话 | 新情况 | 把整行日志发出来，补进本表 |

### 第 2 步：比赛还在进行时，当场确认编码（最快）

比等日志更快。从工作台或源列表拿到这场的 `rtmp://...` 地址，在**本地电脑**用新版 ffmpeg 拉 8 秒看编码：

```bash
ffmpeg -hide_banner -rw_timeout 8000000 -i "rtmp://源地址" -t 8 -f null - 2>&1 | head -40
```

看输出里的 `Video:` 一行：

- `h264`：编码没问题，黑屏另有原因，回到通用第 2 步看日志。
- `hevc` 且带 `(hvc1)` 或 `(hev1)`：国际标准 H.265，服务器升 ffmpeg 7.x 可解。
- `hevc` 但括号里是别的标记：国内私有写法，升级无用，找推流方。

### 升级 ffmpeg（仅当判定是国际标准 H.265 时）

只换预览用的 ffmpeg，不动 OCR 环境，不动 8899。步骤：

1. 在服务器装静态编译的 ffmpeg 7.x（如 `/usr/local/bin/ffmpeg`），先用上面第 2 步的命令对一条已知的 H.265 源验证能解出画面。
2. `.env` 里把预览的 ffmpeg 路径指向新版本（具体变量名以当时代码为准，改前先 `grep -n ffmpeg` 确认），**改完必须 `systemctl restart gif-monitor`，重启会清空所有场的回放缓冲，挑没比赛的空档**。
3. 服务器 `.env` 不随 `deploy-gif` 更新，手工改，并在本地 `.env` 和 `.env.example` 同步记录。

## 第二章：卡顿（画面卡住 → 恢复 → 又卡）

### 第 1 步：对照下表定性

| `reason` 里的原话 | 是什么问题 | 怎么解决 |
|---|---|---|
| `Non-monotonous DTS`（时间戳倒退） | 推流端的时间戳往回跳了，一般是推流端重启或重新推了一次 | 不用改我们的代码，程序 10 秒左右自动重连。频繁出现就找推流方 |
| `Input/output error`，`stderr_tail` 里有 `idle_too_long` | 源服务器说这路流太久没有数据进来，推流方停推或断推了 | 找推流方确认推流端 |
| `Operation not permitted`（且之前在正常播） | 源已经不推了（比赛结束、推流方下播或掉线） | 不用处理，程序每 60 秒探测一次，源恢复就自动接上 |
| `Connection timed out`、`Connection refused`、`Error reading header`、`Server returned 404` | 源短暂中断 | 不用处理。若持续超过几分钟，找推流方确认源 |
| 表里没有的新原话 | 新情况 | 把整行日志发出来，补进本表 |

**判断技巧**：先问操作员「外面的流（别的平台看同一场）卡不卡」。外面也卡 → 基本是源的问题；外面不卡只有工作台卡 → 看下面第 2 步。

### 第 1.5 步：确认这场用的是哪路源（dqd / ls）

一场比赛最多有两路源：`dqd` = 懂球帝自己的高清源（只有少数比赛有），`ls` = 数据源给的直播。8901 开预览时**有 dqd 就用 dqd，没有才用 ls**（2026-11-04 起；之前一律用 ls）。日志里查这场选了哪路：

```bash
journalctl -u gif-monitor --since "2026-11-04 00:00" --no-pager | grep preview_source_resolved | grep 比赛ID
```

- `"live_type": "dqd"` → 已经是懂球帝高清源，卡顿就找推流方。
- `"live_type": "ls"` → 这场没有 dqd 源（或当时 dqd 查询失败，日志里会带 `dqd_error`），没有备用源可换。
- `"live_type": "current"` → dqd 查询失败，但这场预览已经在播，就继续用正在播的那路，不切换（切换会清空已缓存的回看画面）。
- 注意：只在**点开预览那一刻**选源。比赛中途才配上 dqd 源，要让操作员关掉预览再打开才会换过去（换过去后之前缓存的回看画面会清空，换源前想截的先截）。dqd 源自己卡了**不会**自动退回 ls（用户决定不做）。
- dqd 源第一次上线时还没在真实比赛里验证过编码。如果有 dqd 的比赛出现黑屏，按第一章查编码。
- 8899 Dashboard **没改**，仍只用 ls。

---

### 第 2 步：日志里没有退出时，查带宽

转码程序一直正常、但画面仍卡，多半是同时看的场太多、办公室线路不够（2026-10-26 实测办公室线路约 1 MB/s，同时看超过 4 场必卡）。看出问题那段时间有几场在被播放：

```bash
journalctl -u gif-monitor --since "2026-11-04 10:00" --until "2026-11-04 10:50" --no-pager \
  | grep -oE 'GET /preview/[0-9]+' | sort | uniq -c
```

- 只有一两场 → 不是带宽问题，回到通用第 2 步重新核对时间段。
- 很多场同时在看 → 带宽不够，让操作员少开几路小窗。

---

## 附：单场的原始日志在哪

```bash
ls /opt/gif-monitor/tmp/preview/比赛ID/
```

- `ffmpeg.log`：当前这次转码的报错。
- `ffmpeg.prev.log`：上一次退出前的报错（重启时保留）。

问题当场发生时，这两个文件比 journalctl 更完整。
